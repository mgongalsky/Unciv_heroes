# Roadmap: battle simulation sandbox

## Зачем это нужно

Следующая цель проекта — не продолжать архитектурную уборку ради самой уборки, а получить удобную песочницу для разработки и проверки тактических механик .

Мы хотим иметь возможность :

-быстро добавлять и менять правила боя;
-покрывать каждое правило небольшими детерминированными тестами;
-запускать бой без UI;
-ставить AI за обе стороны;
-массово прогонять бои и сравнивать баланс;
-воспроизводить любой интересный или ошибочный бой по seed;
-измерять победителя, длительность и состояние армий после боя .

## Текущее состояние

        Основная миграция BattleScreen на command API завершена.Уже есть :

-единый `BattleCommand` для MOVE, ATTACK, SHOOT и SKIP;
-value - only `BattleCommandResult` и `BattleRejection`;
-application `BattleEvent`;
-один command API для игрока и AI;
-отделённый от UI `BattleScreenCommandMapper`;
-инъекция случайности через `IBattleRandom`;
-unit - и characterization -тесты для damage, movement, morale, luck, команд, событий и AI;
-realistic - field тесты;
-рабочий UI battle loop;
-зелёный focused regression и ручная проверка боя.Этого достаточно, чтобы безопасно разрабатывать отдельные правила.Для удобных балансных экспериментов не хватает headless orchestration полного боя .

## Обязательный последний инфраструктурный срез

### 1.BattlePolicy

Ввести контракт стратегии, которая выбирает действие, но сама его не исполняет.Ориентировочный контракт :

```kotlin
interface BattlePolicy {
    fun chooseCommand(state: BattleState): BattleCommand?
}
```

Точная форма `BattleState` определяется при реализации . Она должна предоставлять только необходимые для решения read - only данные и не давать стратегии напрямую мутировать BattleManager.Критерии:

-текущая логика `AIBattle` сохраняет поведение;
-выбор команды можно тестировать отдельно от её исполнения;
-разные стратегии можно подставлять без изменения battle loop;
-отсутствие допустимой команды выражается явно.

### 2.BattleSimulationRunner

Добавить application -сервис, который запускает полный бой без Scene2D и BattleScreen .

Runner должен :

-принимать BattleManager или подготовленный battle scenario;
-принимать policy атакующей и защищающейся стороны;
-выполнять команды через существующий command API;
-управлять очередью и продвижением хода;
-завершаться при победе одной стороны;
-иметь обязательный `maxTurns`;
-обнаруживать отсутствие прогресса / stalemate;
-собирать application events;
-возвращать value -only результат симуляции.Минимальный результат :

```kotlin
data class BattleSimulationResult(
    val termination: BattleTermination,
    val winnerIsAttacker: Boolean?,
    val turns: Int,
    val events: List<BattleEvent>,
    val seed: Long?
)
```

Имена и дополнительные метрики можно уточнить при реализации .

### 3.Детерминированная случайность

        Добавить seeded -реализацию `IBattleRandom` или другой явный способ создать воспроизводимую последовательность.Критерии:

-одинаковый scenario +policies + seed дают одинаковый результат и transcript;
-seed сохраняется в результате симуляции;
-случайный упавший эксперимент можно повторить одним тестом;
-production random остаётся отдельной реализацией.

### 4.Integration tests полного боя

        Минимальный набор :

1.AI vs AI бой завершается и возвращает победителя .
2.Одинаковый seed создаёт одинаковый transcript и outcome.3.Lethal action публикуется перед `BattleEnded`.4.`maxTurns` останавливает потенциально бесконечный бой.5.Отсутствие прогресса возвращает stalemate, а не зависание.6.Runner не зависит от Gdx, Scene2D и BattleScreen.Тесты отдельных правил по -прежнему должны оставаться маленькими unit - тестами.Runner - тесты проверяют orchestration и несколько ключевых end - to - end сценариев, а не заменяют unit -тесты.

### 5.Batch simulation и метрики

        После готовности runner добавить test / helper для серии из N боёв .

Начальные метрики :

-win rate каждой стороны;
-среднее и медианное число ходов;
-доля stalemate / max -turn завершений;
-средний остаток войск победителя;
-распределение причин завершения.Это исследовательский инструмент, а не unit - тест с жёстким ожиданием конкретного win rate.Статистические assertions следует добавлять только для устойчивых инвариантов и с фиксированными seeds .

## Как добавлять новые механики

        Для каждой механики предпочтителен следующий цикл :

1.Сформулировать правило и ожидаемые крайние случаи .
2.Реализовать чистое правило / use case или расширить существующее.3.Добавить детерминированные unit - тесты.4.Подключить правило к command execution.5.Добавить один integration - сценарий, если меняется взаимодействие нескольких правил.6.Запустить batch simulation и посмотреть на метрики.7.Провести ручной бой и оценить, интересно ли правило ощущается в UI .

Тесты подтверждают корректность и воспроизводимость, но не заменяют игровую оценку.

## Что не блокирует песочницу

        Следующие работы полезны, но не должны задерживать эксперименты с механиками:

-удаление `BattleActionRequest`, `BattleActionResult`, `ErrorId` и legacy `performTurn`;
-удаление legacy domain `BattleEvent` и compatibility adapter;
-дальнейшее разделение большого BattleManager;
-косметическая чистка старых imports, комментариев и логирования;
-перенос всех существующих characterization tests на новый API .

Эти задачи следует выполнять отдельными маленькими срезами, когда они мешают конкретной механике или становятся очевидно мёртвыми.

## Дополнительные архитектурные наблюдения

-Сейчас полный loop принадлежит BattleScreen.После появления runner экран в перспективе должен использовать тот же orchestration - контур либо оставаться тонким интерактивным координатором с эквивалентной семантикой.
-`AIBattle` сейчас одновременно выбирает и исполняет действие.`BattlePolicy` устраняет это смешение ответственности.
-Логика определения победителя не должна дублироваться между BattleManager и `GetBattleResultUseCase`; при реализации runner нужно выбрать один источник истины .
-BattleManager всё ещё зависит от части legacy / LibGDX - моделей.Это допустимо для текущего этапа, пока headless runner реально запускается в тестах без графического окружения .

## Definition of Done инфраструктурного этапа

Этап завершён, когда:

-существуют взаимозаменяемые `BattlePolicy`;
-текущий AI работает через policy без изменения поведения;
-полный AI vs AI бой запускается без UI;
-runner гарантированно завершается победой, stalemate или max - turn результатом;
-симуляция воспроизводится по seed;
-результат содержит минимум winner / termination / turn count / events / seed;
-integration tests покрывают завершение, determinism и защиту от зависания;
-batch helper способен прогнать серию боёв и собрать базовую статистику;
-текущие battle regression tests остаются зелёными;
-ручной бой в BattleScreen продолжает работать .

После этого архитектурную уборку считаем завершённой и переходим к итерациям над интересностью боя.
