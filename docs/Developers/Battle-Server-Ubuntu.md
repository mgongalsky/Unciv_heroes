# Сервер тактических битв на Ubuntu

Модуль `battle-server` запускает отдельный Kotlin/JVM-сервер. Он использует правила битвы из core и контракт battle-protocol. Старый модуль `server` и сетевые сохранения Unciv в этом протоколе не участвуют. Окно игры, OpenGL и desktop-библиотеки для запуска сервера не нужны.

## Подготовка дистрибутива

В Gradle-проекте выполните задачу `:battle-server:distZip`. Она создаёт архив в `battle-server/build/distributions`. Это отдельный шаг: обычная проверка компиляции в IDE не создаёт дистрибутив.

Архив содержит `bin`, `lib`, `assets/jsons`, `deploy` и эту инструкцию. Можно собрать его на Windows и перенести на Ubuntu; графические ресурсы клиента серверу не нужны. Сборка использует общую конфигурацию проекта, поэтому её удобнее выполнить на уже настроенной машине разработчика.

На Ubuntu установите Java 17 или более новую совместимую JVM. Используйте полный headless runtime с модулем `jdk.httpserver`; вручную урезанный jlink-runtime может не содержать его. Java не включена в серверный архив. Параметр `-Xmx256m` ограничивает только Java heap, а не всю память процесса.

Распакуйте содержимое верхнего каталога архива в `/opt/heroic-battle`, чтобы существовали `/opt/heroic-battle/bin/battle-server` и `/opt/heroic-battle/assets/jsons`. При переносе через Windows проверьте право исполнения Linux-скрипта:

```sh
sudo chmod +x /opt/heroic-battle/bin/battle-server
```

## Пробный запуск

```sh
cd /opt/heroic-battle
./bin/battle-server ./assets 8081 127.0.0.1
```

Аргументы: каталог assets, порт, адрес привязки. Их альтернативы — переменные `BATTLE_ASSETS`, `BATTLE_PORT`, `BATTLE_BIND`. Аргументы имеют приоритет. Значения по умолчанию: `assets`, `8081`, `127.0.0.1`; относительный путь assets считается от рабочего каталога процесса.

В другом терминале проверьте каталог:

```sh
curl --fail http://127.0.0.1:8081/v1/scenarios
```

Ожидается JSON с версией протокола и шестью игровыми сценариями. Остановите пробный процесс перед запуском службы на том же порту.

## Служба systemd

Создайте отдельного системного пользователя `heroic-battle` без интерактивного входа, если его ещё нет. Файлы приложения должны быть доступны ему для чтения, а скрипт запуска — для исполнения. Службе не требуется запись в каталог приложения.

```sh
sudo useradd --system --user-group --no-create-home --shell /usr/sbin/nologin heroic-battle
sudo cp /opt/heroic-battle/deploy/heroic-battle.service /etc/systemd/system/heroic-battle.service
sudo systemctl daemon-reload
sudo systemctl enable --now heroic-battle
sudo systemctl status heroic-battle
```

Команда useradd предназначена для первой установки: если пользователь уже создан, пропустите её. Шаблон службы рассчитан на указанные пути; при другой установке измените WorkingDirectory, BATTLE_ASSETS и ExecStart согласованно.

Журнал:

```sh
sudo journalctl -u heroic-battle -n 100 --no-pager
```

## Доступ из Интернета

Оставьте Java-сервер на `127.0.0.1:8081` и направьте HTTPS-запросы через обратный прокси на этом же VPS. Клиент принимает адрес вида `https://battle.example.com`, без пути `/v1`, логина, пароля или query-параметров. Домен ниже — пример; используйте свой домен и действительный TLS-сертификат.

В существующем HTTPS server-блоке nginx для выделенного домена можно использовать:

```nginx
location /v1/ {
    client_max_body_size 4k;
    client_body_timeout 10s;
    proxy_request_buffering on;
    proxy_buffering on;
    proxy_connect_timeout 5s;
    proxy_send_timeout 15s;
    proxy_read_timeout 15s;
    proxy_next_upstream off;
    proxy_pass http://127.0.0.1:8081;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
}
```

Этот фрагмент не создаёт HTTPS server-блок и сертификат. Перед включением проверьте конфигурацию прокси штатным средством проверки. Не добавляйте токены Authorization и тела запросов в журналы. Прокси не должен автоматически повторять команды. Для открытого публичного сервиса настройте ограничения частоты создания и входа в комнаты под доступную нагрузку.

Проверьте `https://ВАШ-ДОМЕН/v1/scenarios` с клиентской машины. Порт 8081 не требуется открывать наружу при размещении прокси на том же сервере.

## Проверка двумя игроками

1. Оба игрока запускают свежую Windows-сборку и открывают Network battle.
2. Первый вводит HTTPS-адрес, загружает сценарии, выбирает сценарий и создаёт комнату.
3. Второй вводит тот же адрес и полученный код комнаты, затем нажимает Join room.
4. Оба нажимают Ready. Открывается поле; управлять можно только текущей стороной.
5. Выполните движение, атаку, выстрел и пропуск. Сверьте очередь, численность и здоровье на обоих экранах.
6. Кратковременно отключите сеть у одного игрока, не закрывая приложение. После восстановления дождитесь обновления. Если остался неопределённый запрос, Retry pending action повторяет его с прежним номером.
7. Завершите бой и сверьте победителя.

## Текущие ограничения

- Комнаты и боевые состояния находятся в памяти. Перезапуск службы завершает все текущие комнаты.
- Клиент удерживает токен комнаты в памяти. Восстановление связи работает в живом экране; продолжение после закрытия приложения пока не реализовано.
- На сервере установлены предел 32 комнаты и срок простоя 30 минут. Чтение состояния считается активностью; открытые экраны периодически опрашивают сервер.
- Повтор последнего запроса возвращает его квитанцию. Более старый запрос отклоняется и не исполняется заново.
- При потере ответа на создание комнаты автоматического восстановления её кода пока нет: неиспользуемая комната истечёт по тайм-ауту. Повтор входа использует сохранённый nonce.
- Сетевой бой предназначен для двух людей. Автоматический выбор действий в интеграционных тестах не подключён к игровому режиму.
- Сетевой экран пока показывает базовое состояние и доступные действия; перенос всех локальных прогнозов, подсветок и анимаций ещё не завершён.

Серверные HTTP-тесты проверяют полный бой и восстановление после потери ответа. Они не заменяют проверку установленной службы, HTTPS, двух графических клиентов и свежего Windows-архива.
