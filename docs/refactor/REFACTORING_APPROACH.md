# Подход к рефакторингу Unciv_heroes

## Основа: Working Effectively with Legacy Code(Michael Feathers)

Рефакторинг ведётся по принципам книги Майкла Физерса.Главная идея : * * legacy код — это код без тестов * * . Прежде чем что -то менять — обеспечиваем страховочную сетку из тестов .

---

## Алгоритм для каждого изменения

        1.* * Identify change points * * — находим конкретное место которое хотим улучшить
        2.* * Find seams * * — ищем швы: места где можно изменить поведение без изменения исходного кода
3.* * Break dependencies * * — разрываем жёсткие зависимости через швы
        4.* * Write tests * * — пишем characterization tests : фиксируем текущее поведение
        5.* * Make changes * * — вносим изменения под защитой тестов
        6.* * Refactor * * — улучшаем код

        ---

## Принципы

-* * Минимальные безопасные шаги.* * Каждый шаг оставляет проект в компилируемом и рабочем состоянии.
-* * Сначала тест, потом изменение . * * Не рефакторим код без страховочной сетки.
-* * Characterization tests . * * Не проверяем правильность — фиксируем текущее поведение . Если тест упал после рефакторинга — что -то изменилось .
-* * Рефакторинг по сущностям.* * Берём одну сущность(
    MapUnit,
    CityInfo и т.д.
) и доводим до конца, а не рефакторим все слои сразу .
-* * Pressure - driven.* * Рефакторим то что реально болит, а не то что красиво по архитектуре.

---

## Техники швов (Seams) применительно к Kotlin

| Техника | Когда применять |
|---|-- - |
| **Lambda Seam * * | Изолировать вызов UI / синглтона внутри метода |
| **Extract and Override * * | Вынести проблемный вызов в `open` метод, переопределить в тесте |
| **Interface Seam * * | Заменить прямую зависимость на интерфейс -порт |
| **Static Setter * * | Быстро подменить синглтон типа `UncivGame.Current` в тестах |
| **Parameterize Constructor * * | Передать зависимость снаружи вместо создания внутри |
| **Extract Method * * | Вынести логику в отдельный метод — создаёт шов и улучшает читаемость |

## Приоритеты(что болит сильнее всего)

### 1.UncivGame.Current в доменной логике
        Место: `CivilizationInfo`, `MapUnit`, `CityInfo`
Проблема: доменные классы знают про UI - синглтон — нельзя тестировать
        Подход: Lambda Seam или Extract and Override для каждого вхождения

### 2.lateinit и Construction Blob в MapUnit
        Место: три конструктора +init блок
        Проблема: непонятный порядок инициализации, падения в редакторе карт
        Подход: Factory метод как единственная точка создания

### 3.Нотификации прямо из доменных объектов
Место: `checkHeroFoodWarning()`, `workOnImprovement()` и др.Проблема: бизнес - логика смешана с UI -эффектами
Подход: Extract Method — отделить вычисление от нотификации

### 4.monsterCivInfo / monsterGameInfo как статические фейки
        Место: `MapUnit.monsterCivInfo`, `CivilizationInfo.monsterGameInfo`
Проблема: редактор карт не может создать объекты без фейковой игры
Подход: явные Factory методы `forEditor()` и `forGame()`

### 5.clone() с незафиксированными полями
        Место: `MapUnit.clone()`
Проблема: `tempBoosts`, `morale`, `luck` не клонируются — реальный баг
        Подход: characterization test который поймает баг, потом фикс

## Что НЕ делаем

-Не строим Clean Architecture сверху вниз « по учебнику»
-Не создаём адаптеры - однострочники ради галочки
-Не переписываем всё сразу
        -Не рефакторим ради красоты — только если это решает реальную проблему
