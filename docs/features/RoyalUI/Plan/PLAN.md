# Royal UI

## Цель и границы

Перенести игровые меню, города, обзоры цивилизаций, героев, информацию об отрядах, диалоги и общие контролы на выбранный Royal Parchment. Дерево технологий сохраняет смысловые состояния. Редактор имеет меньший приоритет, но получает изменения общих компонентов.

Общая миграция частично реализована и не объявляется завершённой. Текущая задача — только план следующего переноса экрана города; изменения игрового кода этим документом не выполняются.

## Архитектура и контракты общей темы

Оформление относится к UI и адаптерам libGDX. Не вводить игровой use case для выбора цвета или рамки. Существующие domain/application, механики, сохранения и сценарные форматы сохраняются, кроме отдельно согласованных функциональных изменений.

Общий слой темы владеет ресурсами. Использовать готовые PNG комплекта, сохраняя прозрачность и углы; сложную рамку не растягивать целиком. Сохранить локализацию, значки в тексте, масштаб шрифта, клавиатуру, disabled-состояния и прокрутку. Проверять совместимость пользовательских skins.

Лента вкладок рисуется как единая поверхность. Сохранить динамическое число страниц, callbacks и доступность выбранной вкладки.

## Исторические этапы 01–03

Подключение общей темы, перенос игровых экранов и регрессия остаются частично завершёнными. Прежняя точка совместного просмотра касалась OptionsPopup и вкладок About, Display, Gameplay. Это историческая граница работы над настройками, а не запрет на отдельно запрошенное планирование города. Остальные экраны автоматически не включаются в новую задачу.

## Новый городской экран: согласованный подход

Начинаем с графики в уже работающем CitySandbox, затем подключаем поведение небольшими законченными этапами. Пользователь подтвердил работу отдельного запуска города. Это не приёмка нового дизайна: он ещё не реализован.

Источник требований города — android/assets/UI_bundles/Heroic-Civs-LibGDX-Handoff/heroic-civs-libgdx-handoff/: README.md, START_HERE_AGENT.md, implementation/FUNCTIONAL_SPEC.md, implementation/ASSET_MAP.md, implementation/LIBGDX_PORT_PLAN.md и design/selected-preset.json. Для города эти документы имеют приоритет над старым Royal UI Bundle. Остальные экраны сохраняют текущую тему.

Зафиксировано: bastion, карта справа, управление слева, azure, brocade, laurel, seam, dense, shield-banner 65%, side-lancet №10. Альтернативы crimson/sage сохраняем как последующую возможность; ближайшая визуальная приёмка — azure. Шесть вкладок: Construction, Tile, Garrison, Hero, Stats, Buildings. Не возвращать мировой HUD, Next Turn или шкалу «две лиги».

### Ответственность слоёв

- UI: компоновка, Drawables, локальные стили, выбранная вкладка/клетка/описание, прокрутка и незавершённый drag. UI не хранит самостоятельную игровую очередь, армию или запас еды.
- Адаптер модели: получает настоящий CityInfo, читает данные, связывает действия с действующими менеджерами и проверяет актуальность города, героя и разрешений. Использует CityScreenContext для обычного и автономного входа.
- Application: координация новой операции только там, где она действительно нужна — например, подтверждение перестановки по актуальному снимку или атомарный обмен. Не создавать универсальную шину команд ради оформления.
- Domain: существующие инварианты населения, армии и снабжения. Новые чистые правила выделять только при обнаруженной потребности, с JUnit4-тестами и производственным вызовом.
- Ресурсы: локальный набор городских стилей и явное владение текстурами. Не переустанавливать default-стили RoyalUi для всего приложения и не освобождать заимствованные атласы/шрифты вместе с экраном.

Предварительные имена компонентов и пути находятся в [перечне будущих файлов](CITY_HANDOFF_FILES.md). Это предложения, не уже существующие API.

### Решения и ограничения

Первая версия сохраняет очередь MutableList<String> и прогресс по названию. Drag-and-drop может переставлять позиции с проверкой актуальности снимка, но не обещает постоянных ID и отдельного прогресса каждого одинакового юнита. Такая новая модель требует отдельного согласования, исторических фикстур сохранений, миграции и проверки завершения/overflow/AI. Не имитировать постоянные ID в Actors.

Сохранить существующие игровые возможности, не перечисленные в веб-прототипе: специалисты, религия, подготовленные события, великие люди, покупка/продажа, размещение улучшений, статусы города. Предварительное распределение: управление населением и специалисты — Construction; религия и великие люди — Stats; подготовленные события — Construction; городские действия — компактная шапка/меню. Расположение уточняется при просмотре, механики не удаляются.

HeroSupplyTable и ArmyManager нельзя считать готовой безопасной командной границей только по их названиям. Риски и необходимые проверки описаны в [исследовании](../Research/CITY_HANDOFF.md). Не менять баланс при исправлении подключения UI.

## Проверки и готовность

Для каждого этапа — BUILD и минимальные целевые native TESTS. Для новой независимой логики — быстрые JUnit4-тесты без движка; для адаптеров и исполнения действий — интеграционные проверки; для Scene2D — GL-проверки размеров, ввода и жизненного цикла. Изменения общих ресурсов требуют соответствующей широкой регрессии.

Golden-эталоны принимать после просмотра фактических изображений и сразу проверять сравнением. Capture-only не является визуальной приёмкой. Прежние неуспешные общие golden-тесты учитывать отдельно; их нельзя объявить исправленными новым городским сценарием.

Первый визуальный результат готов, когда в песочнице показаны выбранные рамки/кнопки/вкладки и настоящая квадратная карта, декор не блокирует ввод, текст читается и ресурсы освобождаются корректно. Полный перенос готов только после подключения реальных действий, сохранения игровых контрактов, проверки сохранений/доступа и переключения обычного входа на проверенный путь.
